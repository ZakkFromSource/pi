# Pi extension inventory

> Generated by `/extentionlist`, plus maintenance notes on how each piece is wired.

## User packages (npm)

- `npm:cc-safety-net@2.4.1`
- `npm:pi-web-access@0.29.0`

Declared in `~/.pi/agent/settings.json` under `"packages"`. Pi installs them into
`~/.pi/agent/npm/node_modules` on startup. Do not copy or commit `node_modules`;
a new machine only needs the settings entry and reinstalls automatically.

## Repo-tracked extensions (`.pi/extensions/`) loaded via global settings pointer

- `.pi/extensions/tps.ts`
- `.pi/extensions/unsloth-summary-sync.ts`

Both live in this repo's `.pi/extensions/` and are listed by absolute path in
`~/.pi/agent/settings.json` under `"extensions"`, so they load from any cwd,
not just the fork directory. Why this pattern:

- The extension loader dedupes by resolved absolute path
  (`packages/coding-agent/src/core/extensions/loader.ts`), so each file loads
  exactly once even when launched from the fork directory, where it is also
  auto-discovered via `.pi/extensions/`.
- Auto-discovery only scans `.pi/extensions/` (project) and
  `~/.pi/agent/extensions/` (global). Old global copies of these files in
  `~/.pi/agent/extensions/` were removed, because two distinct paths to the
  same code would both load and produce duplicate notifications.

## Live global install (repo copy is the tracked source)

- `customizations/extensions/unsloth` (repo) ↔ `~/.pi/agent/extensions/unsloth` (live)

These are identical copies, but only the global one is live. The provider
extension writes `capabilities.json` at runtime (thinking-level metadata), so
pointing the settings at the repo copy would make that runtime write constantly
dirty git status (unless `capabilities.json` were gitignored). The repo copy
therefore serves as the tracked source and backup; on a new machine you copy
repo → global dir (`customizations/extensions/unsloth` →
`~/.pi/agent/extensions/unsloth`).

Note: `unsloth-summary-sync.ts` hardcodes its capabilities path to
`~/.pi/agent/extensions/unsloth/capabilities.json`, so it depends on the live
global unsloth install staying at that location — not on its own file location.

## New machine bootstrap

1. Clone this repo.
2. Copy `~/.pi/agent/settings.json` and `~/.pi/agent/web-search.json` from the
   old machine (both verified secret-free).
3. Copy `customizations/extensions/unsloth` → `~/.pi/agent/extensions/unsloth`.
4. Run `pie` once; npm packages install themselves from the settings entry.

## Privacy: never commit to this repo

This repo is backed up to a public GitHub repo. The following live in
`~/.pi/agent/` and must never be added to version control:

- `auth.json` — API keys / auth tokens (the critical one).
- `sessions/` — private conversation history.

API keys are kept in environment variables, not in any tracked file;
`pi-test.sh --no-env` unsets them for keyless runs.
